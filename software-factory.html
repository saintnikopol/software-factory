The Software Factory

I turned naive prompting across Claude Code, Codex and Pi Agent into a software factory: a full development lifecycle where agents run the floor and the human runs the gates.
Today, 80% of my work is specs and design, 10% is bugs and 10% is improving the factory pipeline itself. Although a single LLM session is not reliable, the Factory turns it into a trustworthy feature conveyor that ships directly into production.

Section 01

What the factory actually is

Eight layers, in the order work moves through them. The numbering is real — this is a pipeline, and an element cannot skip a stage. What matters is the OPERATOR line on each: notice how few of them are still the human, and notice which ones never stopped being the human.

Lifecycle · principal artefacts · the two return paths

1

Intake — goal becomes a graph

Operator: human · agents assist

A goal is decomposed into a machine-readable dependency graph: 402 nodes, each with a criticality tier, a hard calendar horizon, an evidence pointer and explicit blockers edges. Non-technical work — legal, methodology, org — sits in the same graph as the code, because it blocks the same launch. The roadmap is a data structure, not a document, so a machine can topologically sort it and a machine can be wrong about it in a way you can check.

2

Design — the autonomous pre-session

Operator: agent · decisions: human only

Before any question reaches me, an agent runs a design session against the code and docs and produces answers with justifications — not a list of questions. I approve or correct. This inverted the worst part of the loop: I stopped being an oracle answering from scratch and became a reviewer of drafts, which is a far cheaper mental posture.

The hardest rule in the entire system lives here: the orchestrator never decides for the user. It is written down because it was violated — an agent recorded its own defaults as "accepted" before I had replied, and two rounds of rework followed.

3

Dispatch — waves, lanes, and interlocks

Operator: agent · gate: interlock check

Ready nodes are sorted into waves and split into lanes. Each lane gets its own git worktree, its own branch, and — for backend lanes — its own Postgres database, because two lanes sharing one test database deadlocked twice in a day. Before dispatch, an interlock check diffs the lane's file set against every open pull request; a collision on a generated file is resolved on paper, in the task brief, rather than at merge time.

Ceremony is tiered by risk, not uniform. standard lanes get one reviewer and a typecheck. full lanes — migrations, anything data-bearing, anything production-critical — get two independent reviewers on different models, real Postgres tests, screenshot validation, and a full reflection cycle.

4

Execution — one element, one commit

Operator: agent, isolated

An implementer agent works a single element to completion and commits it, together with the documentation that describes it, in the same commit. The target element size is twenty to thirty minutes — chosen deliberately, because the granularity of a commit is the granularity at which a human can interrupt the factory. Nothing is squashed, ever: the commit history is the project journal, and 889 merges preserve it.

worktree per lanemerge commits onlydocs in the same commit
5

Review — non-blocking, fresh context, cross-model

Operator: agent, read-only

After each element a reviewer launches with a clean context window — it has not seen the implementer's reasoning, so it cannot be anchored by it — and read-only permissions. It does not block the chain: the verdict lands in the task journal, blockers to the top of the next iteration, nits to the bottom. An element is not done until a verdict is recorded.

High-risk lanes get two reviewers on different model families. This earns its cost in a specific way: they catch each other's false positives. One reviewer raised a route-precedence blocker that the other disproved from the code — without the second opinion I'd have paid for a fix to a non-bug.

6

Gates — every incident becomes a command

Operator: machine, unconditionally

This is the layer that separates a factory from a very fast intern. A rule that lives in a prompt is a rule the model will forget on the fortieth turn. So each incident is converted into something that runs: a preflight check, a git hook, a millisecond unit test, a generated-artifact drift check. The prose survives only as the explanation of the command.

The gate ladder ends at production reality, and the ordering rule is blunt: compiling is not building, and building is not working. A type-check cannot see a Server/Client boundary; only the bundler can. A green suite on SQLite proves nothing about Postgres. A migration that aborts doesn't degrade the service — it crash-loops it forever, because the container's start command is alembic upgrade head && uvicorn.

7

Release — stage becomes main

Operator: human authorises

Waves do not merge into main. They accumulate on an integration branch, stage, which a preview environment tracks; main moves only by an explicit release merge. That merge is one of the two things I never delegate, because it is the point at which a mistake reaches people.

The release itself is mechanical: a changelog in two formats — one written for users, one for the team — generated from the commit range, then the merge, then a smoke test against production, then a dated tag. The ordering matters. After a merge, nothing but the smoke test proves the state of production; a green pipeline describes the code that was pushed, not the service that came up.

8

Reflection — the factory rewrites its own manual

Operator: agent writes · human authorises

A reflection is mandatory after every wave and every incident. Sessions write proposals; a script harvests them into a machine registry; a consolidator de-duplicates and scores them; and then exactly one step stays manual — I authorise the verdicts. Approved proposals route automatically: a process rule goes into the law file, an engineering change becomes a new node in the roadmap graph, everything else is explicitly deferred or rejected on the record.

81 cycles have produced 436 proposals. 88 shipped, 24 authorised and queued, 59 deferred with a reason, 12 rejected. That ratio is the point: the loop is real precisely because most proposals lose.

The two things that are still, non-negotiably, human

  • Irreversible decisions. Production, deployment, direction. Merging a green pull request is not one of these, and moving it out of the human queue was the single biggest throughput unlock — it freed the actual scarce resource, which is my attention.
  • The verdict on what the factory learns about itself. Agents propose process changes; only I approve them. Otherwise the system optimises its own rules toward whatever is easiest for it to satisfy.
Section 02

The incident ledger

Every guardrail in the factory has a receipt. This is the evidence bank — and it is the reason none of this is hype. Each row is one incident, what it cost in hours or outages, and the check it turned into.

CostWhat happenedThe rule it bought
6.8 h A rebase waited for an editor that could not exist. git rebase --continue in a headless session tried to open a commit message; no TTY, no timeout, no output. It hung for most of a working day before the timeout killed it and the rebase state was lost. GIT_EDITOR=true on every git operation, set in the session environment — not remembered by the agent.
Outage A barrel file shipped a server component to 25 client components. An index.ts re-exported a module that imported next/headers. Re-export drags the whole module, not the named symbol. Type-check was green. Production was down until rollback. A real next build is a required done-criterion for any lane touching a barrel, a dynamic route or a directive — plus a unit test that asserts barrel client-safety in milliseconds.
Crash-loop The guard worked correctly, and that is why production wouldn't boot. A data-bearing migration refused to apply because 10 real rows violated the new constraint. Synthetic fixtures had all passed. The start command runs migrations before the server, so the backend never came up. Read-only query against production data before merging any data-bearing migration. Backfill first, then merge — never the other way round.
47 min Two parallel lanes deadlocked on one test database. Both ran drop_all/create_all against the same schema; lock contention hung both suites with no error, twice in one day. One database per lane, named in the task brief. Parallelism is counted in shared resources, not in agents.
32 min A file was edited but never staged. Everything built locally — the change was in the working tree. What merged was an incompatible pair of props. Production stopped deploying. git show --stat HEAD after every commit. An uncommitted change is not in the pull request.
38 / 39 Teardown wasn't in the definition of done. Session briefs said worktree add and never said worktree remove. Of 39 registered worktrees, 38 were dead — plus one 275 MB directory that outlived its own metadata and broke git operations. Teardown is part of "done", in the checklist of the final element — not a cleanup task that never gets scheduled.
Data loss The orchestrator deleted the user's live worktrees. Their registered paths pointed at the host filesystem, invisible from inside the container — so they looked like stale garbage. They were locked, active, and had uncommitted work in them. Never delete an untracked path without explicit confirmation. Check lock files and live processes first. Prune only from the environment that owns the paths.
460/day The CI bill outran the plan. 1,101 CI-minutes in 2.4 days, after path filters were already in place. Agent throughput turns CI from a background cost into the binding constraint. Heavy gates run only on an explicit label, applied before the final push. Local verification became the primary proof, not the fallback.
Silent "440 passed" against Postgres was actually SQLite in memory. The environment variable was set; the engine was never reached. Three levels of false confidence — done, verified, works — collapsed into one production incident. Every test report must state the engine it actually ran on. A label is not evidence.
×2 A gate that did not run looked like a gate that passed. Two pull requests reached production showing skipped, which in a checks list sits one pixel away from success. Both layers of the product went down. skipping ≠ pass. Readiness is the last run for the head SHA with conclusion success, queried explicitly. Nothing else counts.

Two smaller ones worth telling: seven parallel design sessions exhausted the container's process limit (512) — parallelism has to be counted in PIDs, not just RAM; and a default 60-second "needs attention" timer fired ~15 false alarms in a single run, because a full test suite looks exactly like a stuck agent from the outside.

Section 03

Operating notes

The load-bearing sentences of the process document. Each one is short enough for a slide and defensible from the ledger above.

Mechanical work goes to machines. If a rule can be checked by a command, it must be a command — not a paragraph in a prompt.

The founding principle of the gate layer. Everything else follows from it.

A prompt is forgotten on the fortieth turn. A script is not.

Why 117 lines of process law became a preflight script and a set of hooks.

Done ≠ verified ≠ works.

Three separate levels of false confidence. Each needs its own explicit proof.

A human gate belongs only where the decision is irreversible.

The rule that reclaims the scarce resource: attention, not compute.

The dispatcher's context is a consumable. What isn't written down doesn't exist.

Designing for amnesia is what makes the factory restartable at any moment.

The granularity of interruption is one commit.

Which is why the element size is 20–30 minutes. Human control, quantified.

State, not events. Everything passed between layers is a current desired state — readable twice, or skippable once, without consequence.

Removes acknowledgement races and lost messages from agent coordination.

A gate that didn't run is not evidence.

Bought with two production outages in one afternoon.
